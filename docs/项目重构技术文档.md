# AgentGuard 项目重构技术设计文档

**项目名称：** AgentGuard\
**项目定位：** 情感陪伴智能体风险审查与自动化行为检测系统\
**改造来源：** AgentGuard\
**技术栈：** Python、FastAPI、LangGraph、LiteLLM、Pydantic、GitPython、AST、Docker、Pytest、PostgreSQL、Redis、GitHub API、LLM-as-Judge

***

# 一、项目目标与重构原则

## 1.1 项目目标

AgentGuard 面向情感陪伴机器人 Agent 的持续迭代场景，解决代码、Prompt、记忆策略及业务配置变更可能导致的行为退化问题。

系统通过 GitHub PR 接入代码变更，分析受影响的 Agent 业务能力，动态规划测试用例，利用 Base/Candidate 双版本隔离执行获取真实运行轨迹，结合行为契约、规则断言和 LLM-as-Judge 检测行为回归，最终生成风险报告并决定是否允许合并。

核心检测能力：

1. 记忆连续性：检测历史记忆丢失、召回退化和上下文注入异常。
2. 情绪响应：检测情绪识别错误及情绪响应偏差。
3. 人格一致性：检测 Prompt 或配置修改导致的人格漂移。
4. 安全边界：检测安全策略退化及违规行为。
5. 工具与状态：检测工具调用错误、状态更新异常。

## 1.2 核心设计原则

* 保留 AgentGuard 已有的 Agent 执行框架，避免重复实现。
* 将通用 Agent Runtime 与 AgentGuard 业务逻辑分离。
* 区分代码变更风险与实际行为回归。
* 测试执行由确定性 Python Runtime 管理，LLM 负责分析和评估。
* 所有风险结论必须能够追溯到原始代码、测试用例和 Trace。
* 高风险不直接等于 BLOCK，必须结合实际测试和证据。
* Agent 执行必须具备预算控制、超时控制、工具权限和退出条件。

# 二、整体系统架构

## 2.1 架构分层

系统划分为六个主要层次。

### 第一层：接入层（Integration Layer）

负责接入 GitHub PR，获取 Base/Head Commit、Diff、仓库信息，管理 PR 事件及结果回写。

### 第二层：Agent 编排层（Orchestration Layer）

基于 LangGraph 管理整个 PR 风险评估流程，负责节点编排、状态共享、条件路由、失败恢复和执行控制。

### 第三层：智能分析层（Agent Layer）

包含：

* PR Change Impact Agent
* Test Planning Agent
* Test Case Generation Agent
* Behavior Judge Agent
* Risk Verification Agent

每个 Agent 负责独立业务任务，使用统一的模型调用和结构化输出机制。

### 第四层：执行层（Runtime Layer）

负责 Git Worktree、Docker 环境、Agent Test Adapter、测试执行、Trace 采集和资源清理。

### 第五层：评估决策层（Evaluation & Decision Layer）

负责 Behavioral Contract、规则断言、LLM-as-Judge、Pairwise Evaluation、风险复核和 PASS/BLOCK/REVIEW 决策。

### 第六层：数据与报告层（Storage & Reporting Layer）

负责测试数据、执行记录、Trace、评估结果持久化及 GitHub PR 评论回写。

# 四、核心模块技术设计

## 4.1 Agent Runtime 与 OODA 执行框架

### 目标

保留 AgentGuard 的有界 OODA Agent 执行机制，将其改造成可以服务于代码分析、测试规划和风险分析的通用执行框架。

### 现有文件迁移

现有文件

新职责

runner.py

通用 Agent Runner

graph.py

Agent 内部执行图

nodes.py

通用 OODA 节点及护栏

policy.py

统一预算策略

models.py

执行状态、轨迹及审计模型

llm.py

多角色模型选择

federation.py

可选 Sub-agent 调度

benchmark.py

离线 Agent 评估

### OODA 执行流程

Observe：读取当前任务、代码变更和已有证据。

Orient：分析上下文，判断当前信息是否充分，确定下一步行动。

Decide：选择工具或决定是否需要继续探索。

Act：执行工具调用，获取结果并更新 Agent 状态。

循环直到满足停止条件。

### Harness 控制

统一管理：

* max\_steps
* max\_tool\_calls
* max\_tokens
* timeout\_seconds
* max\_retries
* context\_window
* allowed\_tools

每次执行都记录 Trajectory 和 AuditEvent。

注意：模型推理、工具执行和工作流调度应分别计入预算，不能只在 Agent 外层设置一个最大循环次数。

## 4.2 PR Change Impact Agent

### 输入

```
class ChangeAnalysisInput(BaseModel):
    repository: str
    base_sha: str
    head_sha: str
    changed_files: list[str]
    diff: str
```

### 工具能力

1. read\_file：读取修改文件及上下文。
2. find\_symbol：定位函数和类定义。
3. find\_references：搜索符号引用。
4. analyze\_ast：提取代码结构。
5. inspect\_prompt：分析 Prompt 变更。
6. map\_capability：映射业务能力。

### 业务能力映射

通过 `capabilities.yaml` 建立代码路径与业务能力映射。

例如：

```
capabilities:
  long_term_memory:
    paths:
      - "memory/**"
    related_capabilities:
      - "context_injection"
    test_tags:
      - "memory"
      - "cross_turn"

  emotion_response:
    paths:
      - "emotion/**"
    test_tags:
      - "emotion"

  personality:
    paths:
      - "personality/**"
      - "prompts/**"
    test_tags:
      - "personality"

  safety:
    paths:
      - "safety/**"
    test_tags:
      - "safety"

  tool_state:
    paths:
      - "tools/**"
      - "state/**"
    test_tags:
      - "tool"
      - "state"
```

实际项目中需要根据真实代码仓库补充路径、引用关系和规则，不能只依赖文件名映射。

### 输出

`ChangeImpactReport`：

* changed\_files
* affected\_capabilities
* risk\_hypotheses
* evidence
* recommended\_tests
* exploration\_summary

风险等级分为 LOW、MEDIUM、HIGH。

风险等级主要用于确定测试范围，不直接等同于最终合并决策。

## 4.3 Test Planning Agent

### 输入

* ChangeImpactReport
* Golden Dataset
* 历史测试记录
* 测试预算

### 执行逻辑

1. 根据 affected\_capabilities 检索相关测试。
2. 根据风险等级确定测试深度。
3. 检查现有用例覆盖情况。
4. 对覆盖不足的场景调用 Test Case Generation Agent。
5. 对生成用例进行 Schema 校验。
6. 输出统一测试计划。

### 输出

```
class TestPlan(BaseModel):
    selected_cases: list[str]
    generated_cases: list[str]
    capabilities: list[str]
    priority: str
    estimated_cost: int
```

其中 estimated\_cost 后续可以细分为预计调用次数、Token 和运行时间。

## 4.4 Agent Test Runtime

这是 AgentGuard 相对于原有 AgentGuard 最重要的新工程能力。

### 双版本隔离

```
Evaluation Workspace
│
├── Base
│   ├── Git Worktree
│   ├── Docker Container
│   ├── Agent Adapter
│   └── Trace
│
└── Candidate
    ├── Git Worktree
    ├── Docker Container
    ├── Agent Adapter
    └── Trace
```

### Git Worktree 管理

负责：

* 检出 Base SHA。
* 检出 Candidate SHA。
* 创建隔离工作目录。
* 检查 Commit 是否有效。
* 清理工作目录。

### Docker Runtime

负责：

* 创建独立容器。
* 注入环境配置。
* 启动 Agent 服务。
* 健康检查。
* 资源限制。
* 超时终止。
* 清理容器和网络。

Docker 运行不可信 PR 代码时必须使用受限权限、资源限制和网络策略，不能直接授予宿主机高权限。

### Agent Test Adapter

统一不同 Agent 的执行接口。

```
class AgentTestAdapter:

    async def setup(self, config):
        ...

    async def reset(self, user_profile):
        ...

    async def invoke(self, message, history):
        ...

    async def collect_trace(self):
        ...

    async def teardown(self):
        ...
```

适配器必须有明确的生命周期、异常处理和资源清理约定。

### Trace Collector

采集：

* response
* memory\_read
* memory\_write
* tool\_calls
* state\_delta
* execution\_metadata

建议统一使用 JSON 结构存储，并保留 trace\_id、case\_id、run\_id、version 等关联字段。

## 4.5 Behavioral Contract 与行为评估

### 行为契约

定义 Agent 在不同业务场景下应该满足的要求。

例如：

```
contracts:
  memory_continuity:
    description: "正确保持和召回用户明确提供的历史信息"
    severity: high
    assertions:
      - memory_recall
      - factual_consistency

  emotion_response:
    description: "根据用户当前情绪和上下文提供合适回应"
    severity: medium
    assertions:
      - emotional_relevance
      - contextual_consistency

  personality_consistency:
    description: "多轮对话保持既定人格特征"
    severity: medium
    assertions:
      - personality_alignment
```

### 第一层：Rule-based Evaluation

负责确定性指标：

* 是否召回预期记忆。
* 是否执行预期工具。
* 是否写入正确状态。
* 是否发生异常状态转移。
* 是否违反明确的禁止规则。

### 第二层：LLM-as-Judge

负责语义评估：

* 情绪响应是否恰当。
* 人格表达是否一致。
* 是否理解历史上下文。
* 是否出现行为退化。
* 是否违反行为契约。

### 绝对质量与相对回归

必须同时评估：

1. Candidate 是否符合绝对行为契约。
2. Candidate 相比 Base 是否发生退化。

不能仅使用 Pairwise Judge 代替绝对质量判断。

## 4.6 Risk Verification 与 Merge Gate

### Risk Verification

输入：

* Judge 评估结果。
* 原始测试用例。
* Base/Candidate Trace。
* Behavioral Contract。

检查：

* 引用证据是否真实存在。
* 证据是否支持风险结论。
* 是否存在上下文缺失。
* 是否可以重复复现。
* 是否属于正常行为差异。

### Merge Gate

由确定性 Python 规则引擎负责最终决策。

```
class MergeDecision(str, Enum):
    PASS = "PASS"
    BLOCK = "BLOCK"
    REVIEW = "REVIEW"
```

建议决策：

* PASS：没有达到阻断标准的行为回归。
* BLOCK：确认存在严重且达到阻断标准的回归。
* REVIEW：证据不足、评估冲突、运行失败或需要人工判断。

环境启动失败不能自动视为行为回归，也不能在缺少必要测试时默认放行。

# 七、实验设计与评价指标

## 7.1 测试集建设

初始目标：

* 50～80 条 Golden Test Cases。
* 覆盖 5 类 Agent 业务能力。
* 构造正常变更和故障注入变更。
* 对回归结果进行人工标注。
* 保留原始测试输入、Trace 和 Ground Truth。

这些是项目计划规模，不是已完成数据。

## 7.4 评价指标

* Change Impact Precision / Recall / F1。
* Regression Detection Precision / Recall / F1。
* False Positive Rate。
* False Block Rate。

* PR Evaluation P95 Latency。

所有指标需要通过实际标注样本和实验结果计算。

# 八、开发阶段与实施计划

## Phase 0：现有项目审计

目标：搞清楚 AgentGuard 真实代码依赖。

工作：

* 检查 agent\_exec 每个文件。
* 检查原有 OODA 执行流程。
* 检查 Tool Registry。
* 检查 LiteLLM 调用。
* 检查预算控制。
* 检查 68 项测试的实际覆盖。
* 梳理模块依赖及复用关系。

交付物：代码迁移清单、架构差异文档。

## Phase 1：Agent Runtime 抽取

目标：保留并抽取通用 Agent 执行框架。

工作：

* 统一 Agent State。
* 统一 Tool Registry。
* 统一 Agent Budget。
* 统一 LLM 调用。
* 统一 Trajectory / AuditEvent。
* 建立有界 Agent Runner。

验收：能够独立运行一个带工具调用和预算限制的代码探索 Agent。

## Phase 2：Change Impact Agent

工作：

* PR Diff 获取。
* AST 分析。
* 符号搜索。
* 依赖分析。
* Prompt 变更分析。
* 业务能力映射。

验收：能够识别 PR 影响的业务能力，并输出结构化风险报告。

## Phase 3：测试规划与生成

工作：

* Golden Dataset。
* Test Planning Agent。
* Test Case Generation Agent。
* 测试用例 Schema。
* 风险驱动测试选择。

验收：输入变更报告，输出可执行的测试计划。

## Phase 4：双版本 Runtime

工作：

* Git Worktree。
* Docker 隔离。
* Agent Test Adapter。
* Base/Candidate 执行。
* Trace Collector。

验收：相同用例能够在两个独立版本中运行，并获取结构化 Trace。

## Phase 5：行为评估与风险决策

工作：

* Behavioral Contract。
* Rule-based Evaluator。
* LLM-as-Judge。
* Pairwise Evaluation。
* Risk Verification。
* Merge Gate。

验收：可以发现真实行为回归，生成带证据的风险结论。

## Phase 6：系统工程化与实验

工作：

* FastAPI 服务。
* PostgreSQL 持久化。
* Redis 任务协调。
* GitHub 报告回写。
* Human-in-the-Loop。
* 故障注入实验。
* Benchmark 和性能测试。

验收：完成端到端 PR 自动化风险评估，并产生可复现的实验报告。

# 九、项目技术实现约束

1. 所有 LLM 输出必须通过 Pydantic Schema 校验。
2. 所有 Agent 必须配置最大执行预算和超时。
3. 工具执行必须经过权限控制。
4. 不允许 Agent 随意执行宿主机命令。
5. Base/Candidate 环境必须隔离可变数据。
6. 同一测试用例必须使用一致的测试条件。
7. 每个回归结论必须关联原始 Trace。
8. LLM Judge 不能直接决定最终合并结果。
9. 运行失败、证据不足必须进入 REVIEW 或明确的失败状态。
10. 所有关键执行过程必须支持日志追踪和复现。
11. 每个阶段必须有自动化测试，不允许只通过手动运行验收。
12. 新增能力不得破坏原有上游 PR-Agent 功能。

# 十、最终交付标准

AgentGuard 最终必须实现完整闭环：

* 能够接收 GitHub PR。
* 能够分析代码、Prompt 和配置变更。
* 能够定位受影响的 Agent 业务能力。
* 能够自主探索代码仓库并形成风险假设。
* 能够动态检索和生成测试用例。
* 能够创建 Base/Candidate 隔离执行环境。
* 能够统一接入 Agent 并执行测试。
* 能够采集回复、记忆读写、工具调用和状态变化。
* 能够根据行为契约执行规则与语义评估。
* 能够对疑似回归进行证据复核。
* 能够根据规则生成 PASS/BLOCK/REVIEW。
* 能够将完整报告回写 GitHub。
* 能够通过人工标注、故障注入和对照实验验证效果。

**项目最终定位：不是一个简单的代码审查 Agent，而是一个面向情感陪伴智能体持续迭代的 PR 级行为质量保障系统。**
